# 🧠 멀티에이전트 역추적성과 오케스트레이션 진단

> **핵심 원리**:  
> 1. **"Agent Failed ≠ LLM Failed"** — 복합 에이전트 장애의 다수는 모델 지능 부족이 아니라 시스템 제약(타임아웃, 인코딩, 환경)에서 기인한다.  
> 2. **"Generated ≠ Verified ≠ Approved ≠ Executed"** — AI가 만들었다고 검증된 것이 아니며, 검증되었다고 승인된 것이 아니고, 승인 없이 비가역적 실행을 할 수 없다.  
> 3. **"관측 가능성은 도구가 아니라 질문이다"** — LangSmith를 까는 것이 본질이 아니라, 장애 시 7가지 핵심 질문에 답할 수 있는 실행 흔적이 있는가가 본질이다.  
> 4. **"Framework ≠ Architecture"** — 프레임워크를 많이 설치한다고 좋은 구조가 생기는 것이 아니다. 명확한 역할 분리와 추적성이 최고의 아키텍처다.

## 🔍 1. 실패의 2대 원인 분리 (Model Failure vs Orchestration Failure)

복합 에이전트 시스템이 멈추거나 실패했을 때, 개발자는 흔히 "모델이 멍청해서 답을 못 냈다"며 프롬프트부터 수정하려는 안티패턴에 빠집니다. 그러나 실제로는 **오케스트레이션 실패**가 압도적으로 많습니다:

| 실패 유형 | 실제 원인 예시 | 징후 및 특징 | 올바른 엔지니어링 조치 |
| :--- | :--- | :--- | :--- |
| **오케스트레이션 실패<br/>(Orchestration Failure)** | • 파이프라인 타임아웃 (예: 기본 30초 초과)<br/>• 비동기 호출 간 커넥션 타임아웃<br/>• 파일 경로 / 문자 인코딩(UTF-8) 불일치<br/>• Rate Limit / Quota 고갈 / 도구 인자 파싱 에러 | • 특정 노드 실행 중 급작스러운 단절<br/>• 모델 토큰 생성 전/직후 에러<br/>• 재시도 시 동일 물리 지점에서 반복 실패 | • 타임아웃 임계치 현실화 (30s ➔ 60s+)<br/>• 시스템 인코딩 및 환경변수 정상화<br/>• 네트워크 재시도 및 백오프 정책 수립 |
| **모델 추론 실패<br/>(Model Failure)** | • 프롬프트 지시 불이행<br/>• 잘못된 논리적 추론 / 도메인 환각<br/>• 안전 필터 오작동 | • 실행은 정상 완료되었으나 엉뚱한 결론 출력<br/>• 스키마 유효성 검증(Validation) 위배 | • 시스템 프롬프트 Few-Shot 보강<br/>• 도구 스키마 간소화 및 컨텍스트 다이어트 |

## 🛠️ 2. 장애 원인 9대 진단 순서 (Failure Diagnosis Order)

에이전트 작업이 실패했을 때 **반드시 아래 순서대로 진단**하여, 모델 문제를 가장 마지막에 검증합니다:

```text
FAILURE DIAGNOSIS ORDER (밖에서 안으로, 물리에서 논리로)

1. Infrastructure   ➔ OS 환경, 인터넷 연결, GPU/RAM 리소스
2. Environment      ➔ .env 환경변수, 가상환경, 필수 라이브러리 설치 유무
3. Tool Execution   ➔ 툴 실행 바이너리 존재 유무, 파라미터 타입 일치
4. Timeout / Rate   ➔ 오케스트레이션 타임아웃(30s/60s), API Rate Limit, Quota
5. File / Path      ➔ 절대 경로 유효성, 파일 잠김, UTF-8 문자 인코딩
6. Integration      ➔ 외부 API 상태 코드 (200 vs 500), 서비스 장애 여부
7. Agent Routing    ➔ 슈퍼바이저의 워커 라우팅, 상태 전이(State Edge) 유실 여부
8. Prompt           ➔ 요구사항의 명확성, 제약조건 누락, 모호한 출력 형식
9. Model Reasoning  ➔ (위 1~8번 결손이 없음을 실증한 뒤에만) 모델 자체의 추론 지능 의심
```

## 🚦 3. 가역성 기반 4단계 승인 분리 (`Generated ≠ Verified ≠ Approved ≠ Executed`)

AI의 생성 행위와 실제 세계에 영향을 미치는 실행 행위는 단계를 섞지 않고 분리합니다:

```text
GENERATE (AI 코드/문서 생성)
   ↓
VERIFY (테스트 / Security Gate / 증거 수집)
   ↓
REVIEW & APPROVE (인간 검토 및 명시적 승인)
   ↓
EXECUTE (비가역적 외부 실행)
```

- **🟢 가역적 작업 (Autonomous OK)**:
  - 파일 읽기, 코드 분석, 문서 작성, 요약, 검색, 초안 생성, 로컬 단위 테스트, scratch 임시 파일 작성. (실패해도 1초 안에 되돌릴 수 있음)
- **🔴 비가역적 작업 (Human Approval Mandatory)**:
  - 파일 영구 삭제, Git push, 클라우드 배포, 이메일/메시지 발송, DB 변경/삭제, 결제, 계정 권한 변경. (되돌리기 어려울수록 승인 단계를 물리적으로 강제)

## 🏛️ 4. "관측 가능성은 도구가 아니라 질문이다" (Observability 7대 질문)

LangSmith 같은 거대 관제 SaaS를 억지로 상주시키는 것은 오버엔지니어링입니다. 중요한 것은 장애 시 **아래 7대 질문에 즉시 답할 수 있는 최소 실행 흔적(Minimal Execution Trace)**을 남기는 것입니다:

```text
1. 무슨 작업이 시작되었는가? (Task ID & Planner)
2. 어떤 경로로 실행되었는가? (Architect ➔ Builder ➔ Verification ➔ Auditor)
3. 어디서 멈추거나 실패했는가? (정확한 실패 Step과 타임아웃 여부)
4. 무슨 입력을 받았는가? (파라미터 및 파일 경로)
5. 어떤 검증을 통과했는가? (PASS된 단위 테스트 및 Gate 항목)
6. 무엇이 검증되지 않았는가? (NOT VERIFIED 한계 공시)
7. 누가 최종 판단했는가? (Auditor의 Overall Verdict)
```

현재 Antigravity에서는 `trust_layer.py` + SQLite `memory.db` + `ARCHITECTURE_MAP.md`만으로 이 7대 질문에 완벽히 답할 수 있습니다.

## ⚡ 5. 병렬화 및 에이전트 확장 원칙

- **병렬 실행 원칙**:
  - `DEPENDENT (앞 작업 결과에 의존)` ➔ **순차 실행 (Sequential)**
  - `INDEPENDENT (서로 완전히 독립)` ➔ **병렬 실행 (Parallel)**
  - `UNCERTAIN (의존 여부 불확실)` ➔ **순차 우선 (Sequential First)**
- **에이전트 수 확장 금지**:
  - `에이전트 수 증가 = 컨텍스트 부하 = 디버깅 지옥 = System Bloat`.
  - 필요한 역할(Architect, Builder, Verification, Auditor)의 명확한 경계만 유지하며, 무분별한 에이전트 증식을 영구 차단한다.
