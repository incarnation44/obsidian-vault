# 🎥 눈쟁이의 3캠 4K 60fps 자동 레코딩 & 웹 모니터링 시스템(EJREC) 개발과 한계 완전 분석

## 📌 1. 핵심 요약 (3줄 압축)
1. **문제 정의**: Sony FX3 3대의 FTP 자동 업로드 프리징(40% 확률 멈춤)과 기성 4K 레코더의 비싼 가격(500~900만 원)을 해결하기 위해, PC 기반 자체 녹화·웹 모니터링 프로그램(`EJREC`)을 직접 개발.
2. **시스템 구축**: Blackmagic DeckLink 4채널 캡처보드 + RTX 5080(듀얼 NVENC 하드웨어 가속) + Core Ultra 9 285K + Ubuntu 26.04 기반으로 4K 60fps 3캠 동시 녹화, WebRTC 웹 모니터링, 프록시 자동 변환, 10Gbps NAS 자동 업로드 구현.
3. **현실적 한계와 교훈**: 시스템 구축비 450~500만 원 소요, WebRTC 인코딩 지연(약 400ms), 램 피크 문제 등으로 인해 "소니가 FTP 펌웨어만 고쳐주면 원래 카메라 순정으로 돌아가는 게 낫다"는 실전 엔지니어링 결론 도출.

---

## 🔍 2. 세부 개발 과정 및 시스템 아키텍처

### 1️⃣ 기존 장비의 한계와 자체 개발 계기
- **Sony FX3 내장 FTP 업로드 결함**: 촬영 종료 후 서버 전송 시 약 40% 확률로 카메라가 랜덤 프리징됨 (3대 돌리면 1~2대 확정 멈춤).
- **시중 대안의 한계**:
  - ATEM Mini Extreme ISO: FHD 60fps까지만 지원 (4K 불가).
  - 블랙매직 4K 전용 SSD 레코더: 대당 200~300만 원 (3캠 구성 시 500~900만 원 초과).
  - vMix: 소프트웨어 라이선스 비용 과다.
  - OBS: 다중 채널 개별 소스 동시 녹화(Multi-track ISO) 기본 미지원.

### 2️⃣ `EJREC` 하드웨어 & 소프트웨어 스펙
- **캡처보드**: Blackmagic DeckLink Quad HDMI Recorder (4채널 4K 60fps 10bit 4:2:2 인풋 지원).
- **GPU**: **NVIDIA RTX 5080**
  - RTX 5000번대부터 지원하는 **H.265 4:2:2 10bit 인코딩 하드웨어 가속** 활용 (듀얼 NVENC 칩 탑재로 3채널 4K 60fps 동시 인코딩 가능).
- **CPU & 메인보드**: Intel Core Ultra 9 285K (x8/x8 레인 분할 + 10Gbps 광랜카드 장착).
- **RAM**: **48GB DDR5** (32GB는 3캠 동시 작동 시 초기 램 버퍼 피크로 프레임드랍이 발생하여 48GB로 증설).
- **OS**: Ubuntu Linux 26.04 (LLM 연계 백엔드 서버 구동).

### 3️⃣ 소프트웨어 기능 및 파이프라인
1. **4K 60fps 3채널 무손실 인코딩**: 캡처보드 SDK ➔ RAM 버퍼(1GB) ➔ RTX 5080 듀얼 NVENC 가속.
2. **WebRTC 실시간 웹 모니터링**: 720p 60fps 저지연 스트리밍으로 브라우저에서 3캠 멀티뷰 및 잔여 녹화 시간 모니터링 (Tailscale로 외부 원격 제어 가능).
3. **자동 후처리 & 업로드**: 녹화 완료 즉시 H.264 프록시(Proxy) 자동 변환 후 스토리지 서버로 10Gbps 초고속 자동 업로드.

## ⚠️ 3. 실전 구축 후 마주한 현실적 문제점 (Reality Check)

1. **모니터링 레이턴시 (약 400ms 지연)**
   - 순수 HDMI 선택기는 50ms 미만이나, 웹 스트리밍은 인코딩+디코딩 과정으로 약 400ms 딜레이가 발생해 실시간 촬영 모니터링 시 어색함 발생.
2. **부품값 폭등으로 인한 가성비 붕괴**
   - CPU(50만) + 글카(150만) + 48GB 램(90만) + 2TB SSD(50만) + 캡처보드(100만) = **총 450~500만 원 소요**.
   - 기성 레코더 3대(600만) 대비 엄청나게 저렴하지 않음.
3. **확장성 한계**
   - 카메라를 4대 이상으로 늘릴 경우 PC 1대로는 NVENC 칩과 메모리 대역폭이 포화됨.

## 💡 4. AI(Antigravity)와 사용자 워크플로우에 적용할 점

1. **오버엔지니어링(Over-Engineering) 경계와 '단순성의 원칙'**
   - 소프트웨어로 모든 것을 자동화할 수 있더라도, 하드웨어 비용과 유지보수 복잡도(400ms 딜레이, 램 피크)가 증가하면 실익이 줄어듭니다. 부업 도구나 자동화 웹앱 개발 시 **가장 단순하고 직접적인 최소 비용 구조(MVP)**를 우선 설계해야 합니다.
2. **WebRTC + 하드웨어 가속 미디어 웹앱 아키텍처 레퍼런스 확보**
   - 향후 비전 AI(Vision AI) 카메라 스트리밍이나 실시간 영상 대시보드 웹앱 구축 시 **DeckLink SDK + WebRTC + 듀얼 버퍼 큐** 아키텍처를 표준 패턴으로 활용할 수 있습니다.
3. **메모리 피크(Spike) 방어 설계**
   - 평균 메모리 점유율(22GB)보다 **동시 시작 시점의 순간 피크(Spike)**가 시스템 크래시를 유발한다는 점을 확인. 백엔드 서비스 개발 시 동시 요청 스로틀링(Throttling) 및 큐 버퍼 관리를 필수로 내장합니다.
