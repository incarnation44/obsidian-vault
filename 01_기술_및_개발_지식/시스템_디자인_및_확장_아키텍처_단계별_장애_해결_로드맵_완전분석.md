# 🏗️ 시스템 디자인 & 아키텍처 기초: 트래픽 급증 시 웹 앱이 무너지는 정확한 순서와 단계별 처방

## 💡 핵심 화두: AI 시대에 진정한 소프트웨어 엔지니어의 차별점

* AI를 이용하면 프론트엔드, 백엔드, DB, 배포까지 1인 개발자가 전례 없이 빠르게 구축할 수 있음.
* **"누구나 앱을 만들 수 있는 시대라면, 무엇이 진짜 훌륭한 엔지니어를 만드는가?"**
  * 단순히 코드를 찍어내는 것은 본질적인 난제가 아님.
  * 서비스가 인기를 얻어 1대의 서버와 1대의 DB가 감당하지 못하고 병목이 터졌을 때, **"시스템을 어떤 순서로 확장하고, 무엇을 트레이드오프(Trade-off)로 감수할 것인가?"**를 판단하는 아키텍처 설계 역량이 핵심임.

## 📌 트래픽 단계별 장애 발생 순서와 6단계 아키텍처 진화

### Step 1. 단일 서버 + 단일 DB (출발점)
* **현실적 진실**: 최적화된 20달러짜리 단일 서버 1대와 DB 1대만으로도 초당 수백 건, 하루 수백만 건의 요청(수천 명 동시접속)을 거뜬히 처리할 수 있음.
* **증상**: 대규모 티켓팅/이벤트 오픈 시 수만 명이 동시 접속하면 큐가 밀려 요청 타임아웃 발생.
* **처방**:
  1. **스케일업 (Vertical Scaling)**: 가장 먼저 머신 스펙을 올림 (코드 변경 없이 시간 확보).
  2. **스케일아웃 (Horizontal Scaling) + 로드밸런서 (Nginx 등)**: 동일한 앱 인스턴스를 복제하고 앞단에서 로드밸런서로 트래픽을 균등 분산.

### Step 2. 무상태(Stateless) 서버화와 공유 세션 분리
* **증상 (랜덤 로그아웃)**: 1번 서버에서 로그인했는데 다음 요청이 2번 서버로 들어가면서 세션 메모리가 없어 로그인 풀림 발생.
* **처방**: 서버 메모리에 세션을 두지 않고 **모든 서버를 무상태(Stateless)**로 전환. 외부의 고속 인메모리 저장소(**Redis**)에 세션 정보를 기록하여 모든 서버가 조회 가능하게 함.

### Step 3. DB 커넥션 풀링(Connection Pool) 및 읽기 복제본(Read Replica)
* **증상 1 (커넥션 에러)**: 서버리스 환경이나 복수 서버가 동시에 수백 개의 DB 커넥션을 열어 DB 연결 한도 초과 오류 발생.
  * **처방**: PgBouncer 같은 **Connection Pooler**를 도입해 정해진 수의 커넥션을 재사용.
* **증상 2 (읽기 과부하)**: 전체 트래픽의 90% 이상은 쓰기가 아닌 읽기(조회/스크롤).
  * **처방**: **Primary(쓰기 전용 1대)**와 **Read Replica(읽기 전용 복제본 여러 대)**로 분리.
  * **트레이드오프 (복제 지연, Replication Lag)**: 방금 쓴 글이 복제본에 반영되기까지 0.1~0.5초간 보이지 않을 수 있음. 본인 피드 등 즉시성이 중요한 화면만 의도적으로 Primary에서 직접 읽도록 설계.

### Step 4. 고속 인메모리 캐싱 (Redis)
* **증상**: 프로필 팔로워 수(수백만 행 count)처럼 거의 변하지 않는 무거운 쿼리를 수만 명이 매초 조회하여 DB 리소스 낭비.
* **처방**: 조회 결과를 **Redis 캐시**에 저장하고, 캐시 만료 전까지는 DB에 쿼리를 날리지 않음.
* **핵심 판단**: **"속도를 위해 어디까지 약간 틀려도(Stale) 되는가?"**
  * 팔로워 수 (30초 전 데이터? 무해함 ➔ 적극 캐싱)
  * 은행 계좌 잔고 (0.1초도 틀리면 안 됨 ➔ 캐싱 절대 금지)
  * 이는 코딩 기술이 아니라 **비즈니스와 사용자를 이해하는 엔지니어의 의사결정** 영역임.

### Step 5. 메시지 큐(Queue)와 비동기 백그라운드 워커(Worker)
* **증상**: 회원가입 시 인증 메일 발송, 결제 영수증 발행 등 외부 API 통신이 느려지거나 장애가 나면 사용자 화면 전체가 멈추거나 가입 실패.
* **처방**: 사용자에겐 가입 완료 응답을 즉시 반환하고, 무거운 작업은 **큐(BullMQ on Redis)**에 던진 후 **별도 백그라운드 워커(Worker)**가 비동기로 처리.

### Step 6. 최후의 수단: 데이터베이스 샤딩 (Sharding)
* **증상**: 읽기 복제본으로도 감당이 안 될 정도로 데이터 총량이 커서 단일 머신 디스크에 DB 전체가 담기지 않을 때.
* **처방**: 샤드 키(User ID 등)를 기준으로 데이터를 여러 대의 독립된 DB(샤드)로 물리적 분할.
* **엄청난 대가**:
  * 단일 사용자 조회는 빠르나, 전체 통계나 정렬 같은 **크로스 샤드(Cross-Shard) 쿼리**는 극도로 느리고 복잡해짐.
  * 노션(Notion)이 2,000억 행에 도달했을 때 무중단으로 마이그레이션한 것처럼, 팀이 수년간 미루다 데이터가 한계에 달했을 때만 선택하는 최후의 카드.

## 🛠️ Antigravity 시스템 및 개발 워크플로우 적용점

1. **오버엔지니어링(Over-engineering) 원천 배제**:
   * 초기 프로젝트나 소규모 서비스에 처음부터 샤딩, 마이크로서비스, 복잡한 큐를 덕지덕지 붙이는 안티패턴을 철저히 경계.
   * "단일 인스턴스 ➔ 스케일업 ➔ 로드밸런싱 ➔ 캐시/큐 ➔ 복제"의 자연스러운 병목 해결 순서를 준수.
2. **Redis 단일 인프라의 3대 다목적 활용**:
   * 세션 스토어, 인메모리 캐시, BullMQ 작업 큐를 제각각 다른 솔루션으로 도입하지 않고, **단일 Redis 인프라로 3가지 역할을 통합**하여 아키텍처 복잡도를 극소화.
3. **가역성 기반 설계 의사결정 (ADR) 명문화**:
   * 캐시 만료 주기, Replica 읽기 허용 범위 등은 AI에게 일임하지 않고 사용자/비즈니스 관점에서 트레이드오프를 명확히 기록.
