# Antigravity 모바일 앱 구조 개선 실패 회고록

**작성일시**: 2026년 8월 16일
**작성자**: Antigravity (전일도 사용자 전속 AI)
**분류**: 시스템 장애 및 아키텍처 롤백 기록

---

## 1. 사건 개요
스마트폰용 Antigravity PWA 앱(FastAPI + Llama 3.3 기반)에 실시간 날씨, 웹 검색 기능(DuckDuckGo), 그리고 SQLite를 통한 장기 대화 문맥 유지(Context Retention) 기능을 연동하려다 발생한 구조적 장애 및 롤백 사태. 결과적으로 안정성이 훼손되고 대화 연속성이 끊겨 사용자의 신뢰를 크게 잃었으며, 사용자 지시에 따라 모든 구조를 손대기 전의 원본(단순 1:1 챗 모드)으로 강제 롤백함.

## 2. 핵심 실패 원인 및 아키텍처 결함 분석

### ① 프론트엔드 상태 증발 (Conversation ID Loss)
- **현상**: 사용자가 앱을 닫았다 켜거나 새로고침할 경우, 대화 문맥이 완전히 단절됨.
- **원인**: `app.js`에서 부여받은 `conversation_id`를 브라우저의 `localStorage`에 영구 저장하지 않았음. 이로 인해 페이지 렌더링 시 무조건 `currentConvId = null`로 초기화되어, 백엔드는 매 요청을 완전히 새로운 사용자의 새로운 대화로 취급함.

### ② 컨텍스트 없는 단순 라우터 (Context-less Routing)
- **현상**: "내일 대림동 날씨" 질문 후 이어지는 "비는 안 와?"라는 질문에 엉뚱한 지역(서울)의 날씨를 대답하거나 인식하지 못함.
- **원인**: 백엔드의 도구 라우팅(날씨 등)이 **현재 질문 1문장**의 키워드에만 의존하는 정규식(Regex) 구조였음. 후속 질문에 명시적 지역명(동/시/구)이 누락되면, 즉시 파싱에 실패하고 하드코딩된 기본값(Seoul)으로 덮어써 버리는 치명적 구조적 한계.

### ③ 예외 처리 부재와 할루시네이션(Hallucination) 악순환
- **현상**: "대림제2동"이라는 세부 지역명을 `wttr.in` 외부 API가 인식하지 못하고 500 에러를 반환하자, AI가 이전 대화에서 자신이 변명했던 문구("제공된 데이터는 서울의 날씨만을 포함하므로...")를 그대로 복사하여 우기는 현상 발생.
- **원인**: 외부 API 장애 시 명확한 폴백(Fallback) 메시지를 Context에 주입하지 않았고, 단일 대화방 내에 AI의 과거 "실수"가 지워지지 않고 남아있어 LLM이 일관성을 유지하기 위해 과거의 잘못된 논리를 반복 생성함.

## 3. 최종 조치 결과 (Rollback)
- **백엔드/프론트엔드 복구**: SQLite DB 저장 로직, 사이드바, 도구 자동 라우팅 로직을 모두 파기하고, 가장 초기 버전의 단순 `main.py` 및 `app.js` 코드로 100% 덮어쓰기 복원.
- **서비스 강제 종료**: 실행 중이던 외부 연결용 `cloudflared tunnel` 및 테스트용 `uvicorn` 프로세스를 모두 강제 `kill` 처리하여 완전한 오프라인 상태로 복귀.

## 4. 교훈 및 향후 과제
- 시스템을 고도화할 때는 단순 기능 추가(땜질)가 아니라, 데이터가 흐르는 전체 라이프사이클(프론트 상태 보존 → 백엔드 라우터 문맥 참조 → 외부 API 예외 처리 → LLM 컨텍스트 주입 순서)을 거시적으로 설계해야 함.
- 특히 챗봇에서 "최근 20개 메시지"를 무작정 던져주는 것은 완전한 해결책이 될 수 없으며, Router 자체가 이전 대화의 Entity(지역, 대상)를 인지할 수 있는 지능형 구조가 필수적임.
